# Versioned producer-prefix receipts and transcript reconciliation

Contracts: `runtime-prefix-v1`, `transcript-prefix-v1`; new terminal runtime graph contract `2.0`. Resolves H03. P4-F01 owns acceptance; `ssr.runtime_receipt`, `ssr.transcript.receipt` and reconciliation remain proof authorities. The pinned baseline's receipts validate completed agent graphs and terminal captures; prefix support below is **new work**, not an already available API.

## PR-R01 — What is sealed

One runtime prefix authenticates a completed provider exchange that requested one or more tool actions, together with the earlier completed input/tool-delivery history needed to attribute them. It ends at that exchange's durable accepted MODEL_RESPONSE record, before executing the newly requested actions. It does not wait for their tool-success messages or an AGENT_TERMINAL record. This prevents the publication→acknowledgment→publication dependency cycle.

A prefix cannot originate from a partial stream, malformed tool-call response, refused response with no accepted call, or truncated arguments. It cannot give a current response credit for source that will only be read by another call in the same response. Source evidence must have been delivered in an earlier completed exchange/input binding. A response with multiple calls shares the same prefix, but each operation binds its own call_id, ordinal, tool name and argument hash.

## PR-R02 — Exact receipt bodies and hashes

`$defs.RuntimePrefix`, `TranscriptPrefix`, `OriginCall`, `AttemptIdentity` and `CaptureProof` in `schemas/hardening-v1.schema.json` are closed versioned shapes. Runtime identity includes review/snapshot/task/agent/attempt/control generation and execution-contract hash; input revision and exact request/response hashes are mandatory. `origin_calls` is the exact ordered complete call set in the accepted response, not a model-supplied subset. Source bodies, raw arguments and provider text are absent from project receipt bodies.

Use INPUT_REVISIONS.md's canonical JSON. `runtime_prefix_hash = H("ssr.runtime-prefix.v1", body)`; `prefix_id = "rp1:" + hash`. `transcript_prefix_hash = H("ssr.transcript-prefix.v1", body)` and ID `tp1:` plus hash. H is SHA-256 over domain, one NUL byte, and canonical body; hash/ID are stored alongside the body rather than recursively inside it. Compare exact bytes on idempotent reuse. No random receipt ID, current timestamp or mutable acceptance flag participates in these content identities.

The runtime body binds a digest of the exact delivery manifest (input/source/result identities and their actual delivered byte intervals) and event-chain head. A delivery manifest is an immutable paged host record, ordered by originating request, tool ordinal and returned-range identity; it is not an unbounded array copied into each receipt. Referenced proof closure must resolve under the same snapshot and required policy.

## PR-R03 — Event chain and prefix validation

For a new collaborative attempt initialize `head0 = H("ssr.runtime-genesis.v2", {identity,execution_contract_hash})`. Number canonical source-free runtime records contiguously from 1. Append `head_n = SHA256(b"ssr.runtime-event.v2\0" + bytes.fromhex(head_(n-1)) + n.to_bytes(8,"big") + len(record_bytes).to_bytes(8,"big") + record_bytes)`. Sequence, canonical payload and head are written with the event in the same project transaction. Existing request/response/tool event meanings stay with their owners; the new 2.0 contract freezes the added input binding, delivery-root and termination-reason fields rather than appending unknown fields to the old 1.0 validator.

Prefix validation replays events through end_event_sequence using the 2.0 event reducer. All earlier model exchanges must be closed; the final event is the accepted response with the specified request/response identities. Pending tools are permitted only for the exact calls emitted by that final response. No earlier unresolved side effect can disappear from the graph. The referenced final request must have an OBSERVED input binding for this revision. Confirm every OriginCall equals the parsed accepted response's call tuple.

Seal at most one prefix for `(agent_run_id,end_event_sequence)`. A later seal references the hash of the latest prior sealed prefix for that attempt and has a strictly greater end sequence. It must extend its exact event chain; no branch, skipped sequence, changed identity, or reparenting is accepted. Multiple actions from the same final response reuse the same seal. A new attempt starts its own genesis and cannot extend the predecessor's chain.

An earlier valid prefix stays valid if subsequent inference times out or the task later fails. Later independent failure does not rewrite source already supplied or accepted output. Corruption affecting the earlier prefix itself is different: mark its dependent artifacts unavailable and trigger material revalidation through the owner; never retroactively “repair” its digest.

The added core event projections are closed `$defs.RequestEvent`, `ResponseEvent`, `ToolEvent`, and `TerminalEvent`; the request-observation row is `$defs.RequestBinding`. Reuse the existing event owner and complete event graph reducer, but version these fields explicitly. Request and response events bind the same request hash; response tool calls have unique IDs and contiguous ordinals. Tool result-delivery events must name the real receiving exchange; effect commitment is not delivery. A terminal yielded event requires termination_reason=YIELDED and nonnull yield_intent_id, and must not claim an accepted terminal role artifact. Ordinary RESULT_ACCEPTED requires the exact result_artifact_id. Other existing operational event kinds retain their versioned owner schemas, whose hashes enter the execution-contract digest; they are not accepted as arbitrary new JSON.

## PR-R04 — Transcript prefix, not fake terminal capture

Retain one sensitive capture per actual attempt. Extend its existing append-only record ledger with a prefix-seal table, not a second transcript store. Canonical capture identity, sequence, byte counts and record hashing remain versioned. The new capture format records a completed-request boundary and completed-accepted-response boundary; seal only after all raw request/response material belonging to that exchange is durably appended and its normalized accepted hashes match runtime. A stream chunk alone is never an accepted boundary.

For the new format initialize H("ssr.transcript-genesis.v2", {identity,execution_contract_hash,capture_identity_hash}) and use the same length-framed hash construction under `ssr.transcript-record.v2`, over canonical sensitive record bytes. Completed normalized request/response hashes are separately compared with the exact provider projection; prefix hashing does not reinterpret an old capture format. TranscriptPrefix stores capture_id/identity hash, producer identity, request/response IDs/hashes, last record sequence, prefix record_count, total_bytes and head_hash, plus prior prefix hash. Sequences begin at1, so record_count equals end_record_sequence. total_bytes is the sum of included canonical record byte lengths, excluding chain framing, stored hash columns and the separately stored seal row. Prefix creation must not change the capture status to COMPLETED, freeze its append head permanently, or forge AGENT_TERMINAL. Later records append with their own sequences.

A transcript-prefix validator checks the captured identity, every included record/head, counts, completed exchange boundary and cross-ledger request/response equality. It may continue from a previously verified immutable seal rather than reread the whole history, but validates the parent and new range; a cache without identity/hash/version binding is not proof. Prefix rows and sealed-prefix records reject UPDATE/DELETE through constraints/triggers except separately authorized retention after dependent proof disposal.

## PR-R05 — Required, optional and off policies

REQUIRED needs CaptureProof disposition VERIFIED with nonnull prefix_id/hash and a matching verified transcript prefix. OPTIONAL permits VERIFIED or OPTIONAL_UNAVAILABLE; unavailable uses null IDs and an explicit gap record. OFF requires DISABLED and null IDs. OPTIONAL/OFF do not claim full capture. The runtime event prefix and real source-delivery proof remain mandatory in every mode. Policy is bound to the immutable execution contract, not chosen per tool call to avoid a capture failure.

No ordinary source-free API returns captured bytes. Secret/source-sensitive tool arguments remain in their existing protected capture or live memory, while operations persist only validated source-free projections and hashes. A missing optional capture is not silently treated as a verified required capture.

## PR-R06 — Write and reconciliation order

1. Persist the accepted requesting response and its canonical source-free runtime/input binding. Do not execute an invalid response.
2. In the capture owner, flush the complete exchange, validate and insert the immutable transcript prefix when policy requires/supports it. Commit transcript.db and close that transaction.
3. Verify/reuse the runtime prefix against exact event/input/delivery proof. Persist its row, body/hash, parent association and source-free transcript-prefix link in ssr.db. A capture receipt without matching runtime is not enough.
4. Validate the domain proposal. In one short project transaction, recheck current authority/input and prefix validity, commit semantic artifact/evidence/origin and operation receipt, and either keep ACCEPTANCE_PENDING or make AVAILABLE. Independent lead registration also creates one follow-up task/intent here. Availability/sequence/consumer-wake information commits with the usable state.
5. Return the nonterminal tool result; the requesting agent continues. Its own ACK and eventual terminal receipt are subsequent events, not prerequisites for step 4.

A capture write cannot be made atomic with a project write by nesting Python context managers. Required failure after step 1 leaves no available publication. A prefix may exist with no domain artifact; this is harmless attributable provenance and can be reused by the same original operation. A domain proposal can be durably pending with a unique reconcile intent; never say “registered and runnable” before its required prefix proof exists.

Crash after capture seal/before project link: recover the exact sealed prefix. Crash after runtime-prefix row/before artifact: replay semantic operation without new inference. Crash after availability/before ACK: return the same origin/task IDs. An expired agent may not initiate a new write; authorized host recovery may finish an already prepared original operation only under captured identity and current domain validity checks. Unchanged replay does not allocate another prefix, event sequence or candidate.

## PR-R07 — Physical records and ownership

Add project `runtime_prefix_receipts(prefix_id PK, agent_run_id FK, end_event_sequence, parent_prefix_id FK nullable, body_json, body_hash, UNIQUE(agent_run_id,end_event_sequence))`, `request_input_bindings(request_id PK, agent_run_id FK, input_revision_id FK, request_hash, mandatory_delta_hash, outcome)` and `artifact_prefix_links(artifact_id FK, prefix_id FK, call_id, argument_hash, UNIQUE(artifact_id,prefix_id,call_id))`. Enforce canonical hash/body and compound identity in the receipt owner before writes; FK existence alone is insufficient. Avoid duplicating source metadata already held in delivery records.

Add sensitive `transcript_prefix_seals(prefix_id PK,capture_id FK,end_record_sequence,parent_prefix_id FK nullable,body_json,body_hash,UNIQUE(capture_id,end_record_sequence))`. Owner-validated, immutable prefix rows are imported as hashes/IDs into project storage. Schema migration covers new capture format, old terminal receipt preservation, and no mid-stream reinterpretation. Numeric migration ordinals come from the checked-out ledgers; the protocol versions above are fixed.

The terminal runtime graph 2.0 validates its full chain, all referenced prefix seals and all tool effects. For normal yield use terminal agent status COMPLETED with termination_reason YIELDED; this is completed execution, not completed logical work. Final yield publication additionally requires the full terminal capture/receipt barrier in YIELD_SETTLEMENT.md. An already accepted contextual answer needs only its own valid prefix and is not held hostage to unrelated future turns.
